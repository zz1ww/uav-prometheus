# 容器化说明（Docker 迁移方案）

> 本文说明**为什么用容器**、**怎么把环境搬到容器里**，以及**踩过的坑**。
> 具体操作步骤见 `01-树莓派5-Docker部署Prometheus+FAST-LIO.md`。

---

## 一、为什么放弃原生安装，改用容器

项目原本在 **Jetson Xavier NX** 板载计算机上原生安装 Prometheus，板载机损坏后需要换硬件继续复现。原生方案有三个致命问题：

| 问题 | 说明 |
|---|---|
| **编译不可迁移** | Prometheus 的 `compile_all.sh` 编译产物与机器强绑定，换机必须重编，耗时数小时且极易卡死 |
| **依赖链复杂** | ROS Noetic + MAVROS + Livox SDK + FAST-LIO + SpireCV，任何一个版本不匹配都要重新排查 |
| **ARM 平台适配成本高** | 树莓派是 ARM64 架构，原 x86 上的二进制不能直接用，从源码重编 Prometheus 代价极大 |

**核心思路：环境即镜像。**

> 把已经调通的完整环境（Ubuntu 20.04 + ROS Noetic + Prometheus + 所有依赖）打包成一个 Docker 镜像，
> 换硬件时只需 `docker import` 导入镜像，即可在几分钟内恢复整套环境，**完全绕开重新编译**。

---

## 二、容器方案的两个变体

项目里实际出现过两种容器用法：

### 变体 A：导入预编译镜像（应急复刻，实际使用）

把原板载机上跑通的环境打包为 `prometheus-image.tar`，在树莓派上导入：

```bash
# 导入镜像
cat prometheus-image.tar | docker import - prometheus-image:latest

# 启动容器
docker run -it --name ubuntu20 --network host --privileged prometheus-image:latest bash
```

**关键参数解释：**

| 参数 | 作用 | 为什么必须 |
|---|---|---|
| `--network host` | 容器共用宿主机网络栈 | 无人机要访问雷达（192.168.1.112）、MAVROS 要连飞控串口、地面站要连容器内的 ROS master，全部依赖真实网络 |
| `--privileged` | 容器获得特权 | 需要访问 `/dev/ttyUSB*`（飞控串口）、`/dev/ttyACM*` 等硬件设备，普通容器没有权限 |
| `-it` | 交互式终端 | 需要手工敲命令调试 |

> **注意**：变体 A 是当时为「快速恢复」采取的手段。它的前提是**手头已经有打包好的镜像 tar 文件**。

### 变体 B：从基础镜像重建（可复现方案，文档记录）

如果拿不到镜像 tar，则从干净的 Ubuntu 20.04 ARM 镜像一步步装：

```bash
docker pull docker.1ms.run/library/ubuntu:20.04     # 国内镜像源
docker tag  docker.1ms.run/library/ubuntu:20.04 ubuntu:20.04
docker run -it --name ubuntu20 --network host --privileged ubuntu:20.04 bash
```

容器内再按 `01` 篇的步骤装 ROS Noetic + Prometheus。

> 变体 B 是**完整可复现**的路径 —— 任何人拿到文档都能从零搭出来。这也是整理时优先保留 `01` 篇的原因。

## 三、容器里的硬件访问

容器要控制真实无人机，必须打通硬件：

| 硬件 | 容器内路径 | 要点 |
|---|---|---|
| 飞控（Pixhawk 4） | `/dev/ttyUSB0` | 波特率 921600，需 `--privileged` |
| Livox Mid-360 | 网络（192.168.1.112） | 需 `--network host` + 宿主配好 IP |
| （可选）光流/激光测距 | `/dev/ttyUSB1` | 注意 udev 固定端口号 |

**宿主机侧**需要先给网卡配好雷达网段 IP：

```bash
sudo ip addr add 192.168.1.5/24 dev eth0     # 树莓派 5 网卡名通常是 eth0
ping 192.168.1.112                            # 通即为连上雷达
```

## 四、容器方案的代价（实测踩坑）

容器化解决了「环境不可迁移」，但也带来了新的限制。以下是实测遇到的问题：

### 4.1 内存受限 → FAST-LIO 崩溃

树莓派 5 内存有限，FAST-LIO 的**体素地图无限累积**，实测内存从 2.6G 一路涨到 3.6G 吃满后抛 `std::bad_alloc` 崩溃。

> 完整排查过程见 `02-FAST-LIO排错笔记.md` 问题二。
> **缓解措施**：每次飞行前重启 FAST-LIO，让地图从零开始；不要长时间拿着无人机到处走。

### 4.2 无桌面环境 → 必须关 RViz

树莓派烧的是 **Debian 12 no desktop**，容器内也无需图形界面，因此必须关掉 RViz，否则启动即失败：

```bash
sed -i 's|"rviz" default="true"|"rviz" default="false"|' \
  ~/Prometheus/Modules/FAST_LIO/launch/mapping_mid360.launch
```

### 4.3 仿真模式必须关闭

Prometheus 默认开 `sim_mode=true`（用仿真数据），上真机必须改 `false`：

```bash
sed -i 's|sim_mode" default="true"|sim_mode" default="false"|' \
  /root/Prometheus/Modules/uav_control/launch/uav_control_main_indoor_mid360.launch
```

> **注意路径**：容器内是 `/root/Prometheus/...`，因为容器默认以 root 登录。

### 4.4 ARM 上编译卡死

即使不做全量重编，个别模块在树莓派上编译仍会卡死。处理方式：

```bash
cat compile_all.sh            # 找到卡住的模块
# 单独拎出来，加 -j1 或 -j2 限制并行编译
```

### 4.5 容器内网络工具不全

Ubuntu 基础镜像非常精简，`ping`、`ifconfig`、`netstat` 都没有，需手动装：

```bash
apt update && apt install -y \
  curl wget git vim nano sudo iproute2 dnsutils \
  ca-certificates lsb-release iputils-ping net-tools tmux
```

## 五、容器化带来的收益（对比原生安装）

| 维度 | 原生安装 | Docker 容器 |
|---|---|---|
| 环境恢复 | 重装系统 + 重编 Prometheus（数小时） | `docker import`（数分钟） |
| 硬件迁移 | 每换一台要重来 | 镜像带着走 |
| 环境隔离 | 污染宿主系统 | 与宿主隔离 |
| 依赖冲突 | ROS 版本冲突难解 | 完全隔离 |
| 启动管理 | 手开 4 个终端 | tmux 一键 `start_all.sh` |
| 代价 | —— | 内存/性能开销、无图形界面、硬件需特权 |

## 六、经验总结

1. **容器化的价值在"环境搬运"而非"省资源"** —— 它解决的是「编译不迁移」这个真痛点，不是性能问题。
2. **`--network host` + `--privileged` 是机器人容器化的标配** —— 网络和硬件设备两项缺一不可。
3. **务必留一份"从零可复现"的文档** —— 只依赖 tar 镜像是有风险的（镜像可能在别人手上、或损坏）。`01` 篇就是这份保险。
4. **资源受限平台要提前做减法** —— 关 RViz、关仿真、限制编译并行度、控制地图大小，全是「省资源」动作。
